# Cirno 0.1.3

## Instance layout

The instance root keeps `config.json`, `home/`, `state/` and `workspace/` separate. Agent Home contains personality, instructions, memory and Skills. Runtime state contains browser credentials, conversation databases, Projects, Nodes, Telegram binding, notification and delivery queues, logs and caches. Docker still mounts one instance directory. The global `--home` option selects that instance root; the Agent sees its `home/` subdirectory.

This release targets fresh deployments. There is no importer, fallback or automatic migration from the previous layout. Keep any earlier instance separately. Directory separation does not change Full Access permissions.

## Password changes

Settings → Account shows the registered owner and provides current-password, new-password and confirmation fields. Password validation is shared with registration. A successful change keeps the current browser signed in, revokes other browser sessions, clears server access tokens and reconnects Web UI sockets. Other browsers must log in again. Invalid current passwords, password-rule failures and storage errors remain visible. Passwords are stored only as salted hashes in `state/webui-auth.sqlite3`.

See [instance storage](../home-and-workspaces.md), [configuration](../configuration.md) and [Docker deployment](../docker.md).

## Package and startup boundaries

The engine (`cirno-core`), service (`cirno-server`) and application/SDK facade
(`cirno-ai`) build as separate distributions. The browser frontend stays in
`cirno-web`. Dependencies flow from the application to the service to the engine;
the engine does not import the service. Shared session projection and recovery
belong to the engine.

Run `cirno` to start the service and Web UI in the foreground. Docker uses the
same entrypoint. Separate gateway, webui and terminal-management commands have
been removed. Browser settings retain server restart.

## Settings ownership

Agent heartbeat and its instructions have a dedicated Agent page. Timezone,
conversation coordination and execution display settings have distinct pages.
The server health listener has explicit address/port names, separate from Web UI
transport settings. Cross-conversation limits count all outgoing messages from
each source conversation in a rolling minute. Tool result and tool status
summary lengths have distinct names and descriptions. Configuration and API
field names follow the same distinctions without legacy aliases.

## Conversation control and input provenance

Cirno has the fixed `@cirno` address. Agent reports, Heartbeat, scheduled work,
subagent results and automatic continuation carry runtime source labels; they
are not treated as new human authorization. Cirno can use
`conversations.control` to stop or continue another saved Web conversation and
`goals.control` to inspect, create, replace, update, pause, stop, wait, resume or
delete its Goal. The worker itself still confirms completion.

Stop preserves progress. `/resume` and the Continue control use a configurable
continuation message; Settings → Goals & execution controls its text and whether
it appears in the conversation. Continuation starts a new model request from
saved context; it does not resume a partially generated token stream.

Message actions support branching and editing an idle human message. Editing
replaces that message and later context, preserves its original attachments,
and durably queues the revised request. Branching preserves the source's log
policy. When later history includes tool execution, both actions warn that
context changes do not undo file or external effects. A new conversation
generation rejects writes from old executions. History reset events clear
browser caches after editing or clearing Cirno.

New-conversation commands include `/temporary on|off` and `/ptc on|off`.
`/model <preset>` selects a configured model; names are unique ignoring case.
`/access default|review|full` selects permissions. `/clear` is specific to Cirno.

## Independent operation review

AI review is a third access mode. It reviews blocked filesystem operations and
commands in a fresh context without Cirno memory. Uncertain decisions become
Inbox Actions; related Goals wait. Owner approvals apply once to exact
operations and inspected scripts, with generation checks and a durable wakeup.
AI decisions can be wrong; this mode has an explicit risk warning and does not
replace an operating-system sandbox. See [operation review](../architecture/access-review.md).

## Prompt cache reuse

Task checkpoints now travel with the fresh input as persisted model-only evidence,
rather than rewriting the system prompt. Skill discovery is sorted, and Claude
cache breakpoints include the latest user input or tool result, including the
first turn. Token totals continue to include cached input; cache metrics do not
represent a cost estimate.

## Distribution resources

Source archives retain the core build identity, bundled documentation and browser
assets when rebuilt into wheels outside a Git checkout. Release tests cover this
round trip without a frontend toolchain.
