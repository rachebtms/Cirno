# Cirno 0.2.0

Cirno 0.2.0 introduces the tabbed workspace, modular packages and automatic migration from 0.1.6.

## Tabbed workspace

A persistent Launcher and tab strip bring conversations, Files, file editors, local/SSH Node terminals, embedded websites, Trace and Settings into one workspace. Desktop split groups have independent tab bars and resizable panes. Narrow screens show one selected tab while retaining the desktop groups. Each pane adapts to its own width.

Tab and Launcher order support pointer, touch-hold and keyboard reordering. Launcher order synchronizes across devices. Singleton utilities reuse their tab; Terminal, Files, Browser and Trace support independent tabs. Closing a conversation tab does not stop its work. Unsaved editors and settings use save/discard guards.

The Conversations tab lists ordinary conversations and Projects, with search, sorting, assignment, archive and bulk actions. The Router is separate and cannot be forked. Files supports text editing, Markdown draft previews, images and browser-supported video. Terminal tabs reconnect to their existing server-owned shells after a browser refresh.

HeroUI 3 provides shared controls, dialogs, menus and keyboard interactions. Cirno Snow is the default paired light/dark theme, alongside Ocean, Forest and Graphite. Custom pairs, language and display preferences synchronize through the instance. Notification permission remains device-specific.

Trace is a developer recording tool with a dense event table, source/type filters, pagination and on-demand request inspection. Each tab has Record/Pause and Clear controls; closing it deletes its temporary recording. Request rows include provider-bound messages, system instructions, tool schemas and responses. Temporary conversations are excluded.

The credential vault encrypts personal and SSH records, with per-record Agent visibility and separate optional SSH Node enrollment. User-created credentials default to private; Agent-created or updated records are visible. Metadata/store/delete tools never return plaintext values. See [Tabbed workspace](../workspace.md) for storage, lifecycle and security details.

## Router, models and conversation controls

The Router has ordinary execution tools plus delegation, Project management and supervision. Its prompt favors direct execution for small checks and delegation for larger tasks. Router and Worker personalities are separate; memory is shared. Stable internal IDs are independent of editable public handles. Separate Router message-tool calls produce separate chat bubbles.

Providers and model presets have separate settings pages and stable IDs. Provider balance queries are optional, manually refreshed and disabled until configured. Browser sign-ins belong to the provider instance rather than another application's CLI session. Saved response and stream-inactivity timeouts reach the model adapters; active streams have no fixed total generation deadline.

Interrupted conversations resume from the composer's main Continue button or Router supervision tools. The Router can inspect running/queued/interrupted conversations and concurrency limits, and has reserved execution capacity. Starting another execution clears the previous interruption state; a subsequent failure creates a new one.

Messages wait for server acceptance before the browser discards their drafts. Failed local storage retains the waiting message in memory with an explicit retry. Timed-out unsent messages are removed from the offline transport queue. Late events retain their original conversation generation and cannot interrupt replacement context or recreate deleted conversations.

Editing and branching use saved human-turn boundaries. Internal reports retain their provenance rather than becoming human messages. Removing a confirmed question answer by editing history makes that question pending again. Tool and environment changes are not undone by editing or branching.

## Long-running work

Conversation history, prompt navigation and individual long turns load bounded pages. Tool details and Trace bodies load on demand. Display-only queries avoid copying large in-flight checkpoints. Browser reconnect and foreground recovery refresh ongoing activity without replacing newer events with stale snapshots.

Manual, active and idle compaction share the same implementation. Checkpoint replacement validates the complete pending request before committing it. Failed budget checks and cancellation retain the accepted checkpoint. Omitted-reasoning handoff retains evidence for compaction, and restart recovery preserves completed tool observations without repeating them. See [model context](../model-context.md).

Stop settles checkpoint writes, subprocess cleanup and owned transports. File saves and Agent edits share revision-aware write transactions; cancellation cannot leave a queued write running later. Shell, Node and PTC cleanup drains output while reaping processes. Detached remote Node jobs remain independent of the SSH connection.

Dream uses leased batches with per-input receipts and provenance. Memory journal and checkpoint writes run outside the shared event loop. Memory retrieval supports BM25 and optional local/API embeddings; embeddings remain disabled by default.

Storage, file search, Skills, MCP and automation failures report their underlying errors instead of returning successful empty results. MCP names normalize without collisions; execution and Settings share Skill metadata parsing. Telegram shutdown drains owned workers, and uncertain new-message delivery is not silently replayed.

## Storage and migration

Conversation storage belongs to the instance rather than the default workspace. Startup automatically imports published v0.1.6 conversation databases, checkpoints, pending inputs and automations. Distinct histories sharing an ID retain separate IDs. Configuration records `lastRunVersion`; interrupted migration resumes before the Agent starts. Originals and an import report remain under `state/migrations/`. See [instance migration](../migrations.md).

Full-instance backups include configuration, account, conversations, memory, personalities, Skills and managed tool state. Extra folders can be selected from workspace and detected CLI data suggestions. The full image persists user Python packages and CLI login configuration in the instance volume, separately from Cirno's own environment.

Settings exposes file upload limits, model request controls, compaction, AI operation review and optional capabilities. Browser validation and server upload ingress use the same saved limits. Usage-chart details stay visible after a click or tap. Signed media downloads use bounded streaming and preserve their opened file snapshot across atomic replacement.

## Packages and API

Memory, usage, credentials, execution and server concerns have explicit package boundaries. Frontend features own their state, actions and views. Shared panel contracts declare multiplicity and resource lifetime. A general plugin platform is deferred.

Service endpoints use `/v0/`, including bootstrap, accounts, WebSockets, transfers, MCP authorization callbacks and health. The prefix follows the API major version. Unversioned endpoints are not redirected. See [API versions](../development/api.md).

## Upgrade

Select `ghcr.io/rachebtms/cirno:0.2.0` or `ghcr.io/rachebtms/cirno:0.2.0-full`. Preserve the instance volume, external workspace and CLI data mounts, environment and reverse-proxy network. Stop active work before recreating the container, then refresh the browser or installed Web app.

The importer updates configured WebSocket paths and public URLs to `/v0/`; external clients and proxy path rules must follow them. See [Docker upgrade steps](../docker.md#upgrading-from-016). Replacing a slim container with the full image selects the bundled embedding model for blank paths while preserving custom paths and the saved enable switch.
