# Cirno 0.2.1

## Setup and Router behavior

First setup includes theme selection and compact Provider/Models navigation.
Once a model is connected, a one-time introduction asks about the assistant's
personality, how to address the owner and the owner's background. The Router
saves assistant identity in `SOUL.md`, user information in `USER.md` and empties
`BOOTSTRAP.md` when the introduction is finished or skipped.

Built-in instructions now allow those profile writes directly, removing the
conflicting Dream-only rule. Router instructions distinguish brief checks from
paper reading, research, development and experiments that belong in Workers.
Router replies use the message tool; a missing tool reply triggers a bounded
correction and an explicit error if correction fails.

Agents can withdraw pending questions with `user.cancel_ask`. Answered or
cancelled questions become read in the Inbox. Cancellation belongs to the
originating conversation and history generation; replay cannot reopen it.

## Trace and interface fixes

- Trace keeps its contents visible during background polling.
- Download a complete recording as ZIP, including events, API messages, tool
  definitions and responses. Repeated message prefixes share stored JSON blobs.
- Copy the currently displayed inspector section. Load more first to include
  additional pages in the clipboard; ZIP export includes the entire recording.
- Settings content stays centered in desktop and split panes. Short controls
  share their label's row, provider icons have consistent spacing, and chat
  header controls use the same idle appearance.
- History accepts events with input-origin provenance alone, including first
  awakening and scheduled inputs. Failed history loads show an error and retry
  action instead of an empty conversation.

## Upgrade

Use `ghcr.io/rachebtms/cirno:0.2.1` or `ghcr.io/rachebtms/cirno:0.2.1-full`,
keeping the existing instance volume and external workspace mounts. Startup
automatically advances 0.2.0 configuration to 0.2.1; conversations, profiles and
settings are retained. Existing owners are not sent through first registration
again. Instances on 0.1.6 follow the registered migration chain.

See [Docker deployment](../docker.md) and [instance migration](../migrations.md).
